# travel-agent 学习笔记：为什么 pip 装了依赖，PyCharm 还是满屏爆红？

> 说明：这篇笔记记录的是从「单文件脚本」到标准项目的排查过程。文中早期的 `test.py`、`get_weather.py`、`get_attraction.py` 等文件名，重构后分别对应 `travel_agent/cli.py`、`travel_agent/tools/weather.py`、`travel_agent/tools/attractions.py`。最新结构以根目录 `README.md` 为准。

## 一、先给结论

**不是代码里少写了 import，也不是 `pip install` 的命令写错了，而是「装包的环境」和「PyCharm 用的环境」不是同一个。**

这台机器上至少有三套 Python：

| 位置 | 用途 | 依赖情况 |
| --- | --- | --- |
| `C:\Users\chen\AppData\Local\Microsoft\WindowsApps\python3.11.exe` | PyCharm 项目当前选的 `Python 3.11` | **空的**，没有 openai / requests / tavily |
| `C:\Users\chen\.workbuddy\binaries\python\envs\default\Scripts\pip.exe` | 终端里 `pip` 实际指向的 WorkBuddy 环境 | 没有本项目依赖 |
| `C:\Users\chen\.workbuddy\binaries\python\versions\3.13.12\python.exe` | 终端里 `python` 实际指向的 3.13 | 没有本项目依赖 |
| `C:\Users\chen\AppData\Local\Programs\Python\Python311\python.exe` | 另一套完整的 Python 3.11 | **依赖齐全**：openai 2.30.0、requests 2.33.0、tavily-python 0.7.23、python-dotenv |

关键证据：

- PyCharm 的 `.idea/misc.xml` 里写的是 `project-jdk-name="Python 3.11"`。
- PyCharm 的全局解释器表里，`Python 3.11` 指向 `WindowsApps\python3.11.exe`，这是 Windows Store 版 Python，`pip list` 里没有本项目依赖。
- 终端里 `pip -V` 指向 WorkBuddy 的 `envs/default`，而 `python -V` 指向 3.13.12，**pip 和 python 本身就不是一套**。
- 你贴的安装输出里只有 pip 升级提示，没有 `Successfully installed ...`，说明那次安装很可能没有真正完成。

所以：`pip install` 成功与否，和 PyCharm 能不能看到包，是两件事。IDE 只认它自己配置的那个解释器。

## 二、这个项目原来哪里没构建好

### 1. 没有依赖清单，环境不可复现

原来只有几个 `.py` 文件，没有 `requirements.txt`。换一台机器、换一个解释器，就不知道要装什么版本。

**已补：** `requirements.txt`

```text
openai>=2.0,<3
requests>=2.32,<3
tavily-python>=0.7,<1
python-dotenv>=1.0,<2
```

### 2. 没有 `.env` 示例，密钥配置全靠猜

代码读 `DEEPSEEK_API_KEY`、`TAVILY_API_KEY`，但项目里没有任何地方告诉使用者这两个变量要放在哪、叫什么。

**已补：** `.env.example`，复制成 `.env` 后填 Key 即可。

### 3. 没有 `.gitignore`，密钥和缓存容易被提交

`.env`、`__pycache__`、`.idea`、虚拟环境都不应该进 Git。

**已补：** `.gitignore`

### 4. 代码不会自动加载 `.env`

原来只用 `os.getenv()`。如果在 PyCharm 里直接点运行，而没有在 Run Configuration 里配环境变量，读到的就是 `None`。

**已改：** `test.py` 启动时 `load_dotenv()`，优先读项目根目录的 `.env`。

### 5. 大模型调用把异常吞成了普通字符串

原来的 `OpenAICompatibleClient.generate()`：

```python
except Exception as e:
    print(...)
    return "错误:调用语言模型服务时出错。"
```

这会让 ReAct 主循环把「错误字符串」当成模型输出，继续用正则找 `Action:`，最后报一个完全不相关的解析错误，真正的原因（Key 错、模型名错、网络错）被埋掉了。

**已改：** 定义 `LLMError`，失败时抛出；主循环捕获后直接终止并打印真实原因。

### 6. 网络请求没有超时

`requests.get(url)` 和 OpenAI 调用都没有 timeout。网络一卡，程序可能一直挂着。

**已改：**

- 天气请求 `timeout=10`
- LLM 客户端 `timeout=60`（可用 `LLM_TIMEOUT` 覆盖）

### 7. 模型名和地址硬编码

原来：

```python
BASE_URL = "https://api.deepseek.com"
MODEL_ID = "deepseek-flash"
```

`deepseek-flash` 不一定是你的账号可用的模型名，而且换服务商要改代码。

**已改：**

```python
model=os.getenv("DEEPSEEK_MODEL", "deepseek-chat")
base_url=os.getenv("DEEPSEEK_BASE_URL", "https://api.deepseek.com")
```

如果确实要用 `deepseek-flash`，在 `.env` 里写 `DEEPSEEK_MODEL=deepseek-flash` 即可，不用改代码。

### 8. `test.py` 是「脚本流水账」，不是可复用模块

原来所有逻辑写在模块顶层：

- `import test` 就会立刻建客户端、发请求
- 没有 `main()`
- 没有 `if __name__ == "__main__"`
- 解析逻辑和主循环混在一起，很难单独测试

**已改：** 拆成 `build_client()`、`truncate_extra_pairs()`、`parse_action()`、`parse_finish()`、`parse_tool_call()`、`main()`，并加上入口保护。

### 9. ReAct 解析太脆弱

原来的解析：

```python
action_match = re.search(r"Action: (.*)", llm_output, re.DOTALL)
```

`re.DOTALL` + 贪婪匹配会把 `Action:` 后面的所有内容都吃进去；如果模型多输出一轮，就可能解析出奇怪的东西。另外：

```python
final_answer = re.match(r"Finish\[(.*)\]", action_str).group(1)
tool_name = re.search(r"(\w+)\(", action_str).group(1)
```

只要格式稍微偏一点，`.group(1)` 就直接抛 `AttributeError`。

**已改：**

- `Action` 只匹配单行：`^\s*Action:\s*(.+?)\s*$`
- `Finish[...]` 用 `fullmatch`
- 工具调用用 `fullmatch`，并检查参数里有没有解析不掉的残留
- 所有解析失败都转成 `Observation` 让模型自我修正，而不是让程序崩掉

### 10. `get_attraction.py` 顶层 import Tavily

原来：

```python
from tavily import TavilyClient
```

只要没装 `tavily-python`，`dics.py` 就 import 失败，整个项目连天气都查不了。

**已改：** 延迟到函数内部 import，并给出「请运行 pip install -r requirements.txt」的明确提示。

### 11. `TAVILY_API_KEY` 读了但没用

原来 `test.py` 里有一行：

```python
TAVILY_API_KEY = os.getenv("TAVILY_API_KEY")
```

但后面完全没用到，属于误导性代码。**已删除**。Tavily Key 由 `get_attraction()` 自己读取。

### 12. 天气请求不够健壮

原来没有：

- 超时
- User-Agent
- 城市名 URL 编码

**已改：** 加上 timeout、UA，并用 `urllib.parse.quote` 编码城市名。

### 13. 没有类型标注和静态检查

原来函数参数、返回值都没有类型，IDE 很难做补全和检查。

**已改：** 关键函数补了类型标注；用 Ruff 检查通过。

## 七、几个容易混淆的点

### `pip install` 成功 ≠ PyCharm 能用

`pip` 是某个 Python 解释器附带的工具。你敲的 `pip` 属于哪套 Python，包就装进哪套。PyCharm 只认自己配置的解释器。

排查命令：

```bash
pip -V
python -V
```

如果两个输出的路径不一致，就说明 `pip` 和 `python` 不是一套。

在 PyCharm 里看：`Settings` → `Python Interpreter`，右上角会显示解释器路径。

### Tavily CLI 的 OAuth 凭证 ≠ `TAVILY_API_KEY`

之前配置的 `tvly` CLI 用的是浏览器 OAuth，凭证存在 `~/.tavily/config.json`。  
`tavily-python` SDK 用的是 `TAVILY_API_KEY`，两者不是同一个东西。要用 Python SDK，需要在 Tavily 后台创建一个 API Key，填到 `.env`。

### Windows Store 版 Python 的坑

`WindowsApps\python3.11.exe` 是一个应用执行别名，指向 Store 安装目录。它可以运行，但：

- 包目录在 `Program Files\WindowsApps` 下，权限特殊
- 很容易和 `python.org` 安装版、WorkBuddy 自带 Python 混淆
- PyCharm 自动检测时经常优先选它

所以更推荐用 `python.org` 安装版或项目虚拟环境。

## 九、补充：`copy .env.example .env` 和 `export` 到底做了什么

### `copy .env.example .env`

这不是什么特殊命令，就是**复制一个文件**：

- `.env.example`：模板文件，里面是占位符，可以提交到 Git，给别人看需要哪些配置。
- `.env`：真正的本地配置文件，里面填真实 Key，**不要提交到 Git**（`.gitignore` 已经忽略了它）。
- `test.py` 里的 `load_dotenv()` 会自动读取项目根目录的 `.env`，把里面的键值加载成环境变量。

所以这条命令的作用只是「把模板复制一份，准备填真实值」。

不同终端的写法：

| 终端 | 命令 |
| --- | --- |
| Windows CMD | `copy .env.example .env` |
| PowerShell | `Copy-Item .env.example .env` |
| Git Bash | `cp .env.example .env` |

如果 `.env` 已经存在，就**不要再复制**，否则可能覆盖你已经填好的内容。直接编辑 `.env` 即可。

### `export DEEPSEEK_API_KEY=...` 成功了吗？

`export` 本身通常能成功，但它的作用范围很有限：

- 只在**当前这个终端会话**里有效。
- 只对**从这个终端启动的子进程**有效。
- 关掉终端就没了。
- **不会写进 `.env` 文件**。
- **PyCharm 点绿色运行按钮时不会继承**这个终端的变量。
- 新开一个终端也看不到。

所以：

- 如果你在**同一个终端**里先 `export`，再运行 `python test.py`，那这次运行是能读到的。
- 如果你在 PyCharm 里点运行，或者在另一个终端运行，就读不到。
- 现在的 `.env` 里仍然是 `sk-your-deepseek-key` / `tvly-your-tavily-key` 这样的占位符，说明真实 Key 并没有写进文件。

检查当前终端有没有设置（不会打印密钥）：

```bash
# Git Bash
[ -n "$DEEPSEEK_API_KEY" ] && echo "DEEPSEEK_API_KEY: set" || echo "DEEPSEEK_API_KEY: unset"
[ -n "$TAVILY_API_KEY" ] && echo "TAVILY_API_KEY: set" || echo "TAVILY_API_KEY: unset"
```

```powershell
# PowerShell
if ($env:DEEPSEEK_API_KEY) { "DEEPSEEK_API_KEY: set" } else { "DEEPSEEK_API_KEY: unset" }
if ($env:TAVILY_API_KEY) { "TAVILY_API_KEY: set" } else { "TAVILY_API_KEY: unset" }
```

不要用 `echo %DEEPSEEK_API_KEY%` 这种方式检查，它会把完整密钥打印到屏幕上。

### 推荐做法

把真实 Key 写进 `.env`，不要依赖 `export`：

```bash
notepad .env
```

把这两行改成真实值：

```text
DEEPSEEK_API_KEY=sk-你的真实key
TAVILY_API_KEY=tvly-你的真实key
```

保存后，无论从 PyCharm 运行还是从终端运行，`load_dotenv()` 都能读到。

另外，代码现在会识别示例占位符：如果 `.env` 里还是 `sk-your-...` / `tvly-your-...`，会直接提示「还是示例占位符」，而不是拿假 Key 去请求、最后只看到 401。

## 十、补充：venv 里报 `ModuleNotFoundError: No module named 'dotenv'`

这是切到项目 `venv` 后遇到的第二个环境问题。

### 现象

```text
File "test.py", line 9, in <module>
    from dotenv import load_dotenv
ModuleNotFoundError: No module named 'dotenv'
```

然后继续跑还会报：

```text
ModuleNotFoundError: No module named 'requests'
ModuleNotFoundError: No module named 'openai'
```

### 原因

`venv` 是新建的，`pyvenv.cfg` 里 `include-system-site-packages = false`，它不会继承系统 Python 已经装好的包。所以即使全局 Python 有 `openai`、`requests`、`tavily-python`，这个 venv 里也不一定有。

另外，venv 里还出现了一个容易混淆的包：

```text
dotenv          0.9.9   Deprecated package
python-dotenv   1.2.4   Read key-value pairs from a .env file
```

`dotenv` 是一个已经废弃的同名包，不是 `python-dotenv`。两个包都会往 `site-packages/dotenv/` 里写文件，容易互相覆盖。正确要装的是 **`python-dotenv`**，不是 `dotenv`。

### 修复

在项目根目录，用 venv 自己的 pip 安装：

```bash
venv\Scripts\python.exe -m pip install -r requirements.txt
```

如果官方源慢，可以用国内镜像：

```bash
venv\Scripts\python.exe -m pip install -r requirements.txt ^
  -i https://pypi.tuna.tsinghua.edu.cn/simple
```

装完后验证：

```bash
venv\Scripts\python.exe -c "import openai, requests, tavily, dotenv; print('OK')"
```

本次已经装好并验证通过：

```text
openai 2.54.0
requests 2.34.2
tavily OK
dotenv OK
```

### 关键习惯

**每次新建 venv 后，第一件事就是装依赖：**

```bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

不要以为「全局装过了，venv 里就能用」。venv 的设计目的就是隔离，默认不继承全局包。

### 不要装错包

| 想要的功能 | 正确包名 | 容易装错的包 |
| --- | --- | --- |
| 读取 `.env` | `python-dotenv` | `dotenv`（已废弃） |
| Tavily SDK | `tavily-python` | `tavily` |
| OpenAI SDK | `openai` | 无 |

如果已经误装了 `dotenv`，可以尝试：

```bash
venv\Scripts\python.exe -m pip uninstall -y dotenv
venv\Scripts\python.exe -m pip install --force-reinstall python-dotenv
```

本次 venv 里两者并存但 `from dotenv import load_dotenv` 已能正常工作；如果以后遇到 `ImportError: cannot import name 'load_dotenv'`，优先怀疑这个同名包冲突。

## 十一、项目结构与 venv 是什么

### 项目结构

```text
travel-agent/
├─ main.py                     # 兼容入口：python main.py
├─ travel_agent/
│  ├─ __main__.py              # python -m travel_agent
│  ├─ cli.py                   # 命令行参数与启动
│  ├─ config.py                # 环境变量与 Settings
│  ├─ llm.py                   # 大模型客户端
│  ├─ prompts.py               # 系统提示词
│  ├─ agent.py                 # ReAct 循环与解析
│  └─ tools/
│     ├─ weather.py            # 天气工具
│     └─ attractions.py        # Tavily 景点工具
├─ tests/                      # pytest 单元测试
├─ docs/                       # 学习笔记
├─ requirements.txt            # 运行依赖
├─ requirements-dev.txt        # 测试与 Ruff 依赖
├─ pyproject.toml              # 项目元数据与工具配置
├─ .env                        # 真实 Key（不提交）
├─ .env.example                # Key 模板
├─ .gitignore
├─ venv/                       # 项目专用虚拟环境，约 70 MB
└─ .idea/                      # PyCharm 配置
```

运行链路：

```text
main.py / python -m travel_agent
  → travel_agent.cli 读取 Settings
  → TravelAgent 调用 OpenAICompatibleClient
  → 模型输出 Thought + Action
  → agent.parse_action() 解析
  → tools.available_tools 执行 get_weather / get_attraction
  → 把结果作为 Observation 写回历史
  → 继续循环，直到 Finish[...]
```

### venv 是什么

`venv` 是 Python 自带的虚拟环境工具。执行：

```bash
python -m venv venv
```

会在项目里创建一个 `venv/` 目录，里面有：

- `Scripts\python.exe`：这个环境自己的 Python 解释器
- `Scripts\pip.exe`：这个环境自己的 pip
- `Scripts\activate`：用来把当前终端切到这个环境
- `Lib\site-packages\`：这个环境自己安装的第三方包

关键点：**venv 默认不继承全局 Python 的包**。  
这个项目的 `pyvenv.cfg` 里写着：

```text
include-system-site-packages = false
```

所以：

- 全局 Python 里装了 `openai`，不代表 `venv` 里有
- 在 `venv` 里 `pip install`，包只会进 `venv\Lib\site-packages`
- 删除 `venv/`，全局 Python 完全不受影响

### 为什么需要 venv

1. **隔离依赖**：项目 A 用 openai 2.x，项目 B 用 openai 1.x，互不打架。
2. **可复现**：`requirements.txt` 记录依赖，换机器能重建。
3. **不污染全局**：不用往系统 Python 里塞一堆包。
4. **可随时重来**：删掉 `venv/`，重新创建即可。

### 常用命令

创建：

```bash
python -m venv venv
```

激活（可选，只是改当前终端的 PATH）：

```bash
venv\Scripts\activate
```

装依赖：

```bash
pip install -r requirements.txt
```

退出：

```bash
deactivate
```

不激活也能直接用：

```bash
venv\Scripts\python.exe test.py
```

PyCharm 里不需要 `activate`，只要把解释器选成：

```text
C:\Users\chen\Desktop\hello-agents\code\travel-agent\venv\Scripts\python.exe
```

### 常见误区

- **「全局装过了，venv 里就能用」**：不能，venv 是隔离的。
- **「venv 要提交到 Git」**：不要。提交 `requirements.txt`，别人自己创建 venv。
- **「activate 是必须的」**：不是。它只是方便你直接敲 `python`；直接写 `venv\Scripts\python.exe` 也一样。
- **「venv 是 conda」**：不是。`venv` 是 Python 标准库自带的轻量方案，不管理 Python 版本本身。
